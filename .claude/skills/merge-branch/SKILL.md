# 리뷰 후 브랜치 병합
PR 없이 로컬에서 병합합니다(AGENTS.md "작업 흐름" 4번). 병합·푸시·배포·Notion 쓰기를 하므로 모델이 스스로 불러오지 않고, 프로젝트 오너가 `/merge-branch <브랜치>`로 직접 실행합니다. 오너가 대화에서 "병합해 주세요"처럼 요청하면 같은 절차를 따릅니다. 어느 쪽이든 이번 대화에서 그 브랜치의 병합을 명시적으로 요청했을 때만 진행합니다. 다른 브랜치나 이후 작업으로 승인을 넓히지 않습니다. 브랜치를 여러 개 받으면 받은 순서대로 하나씩 처리합니다.

1. 확인: `git status`에 커밋하지 않은 변경이 있으면 멈추고 알립니다(건드리지 않음). `git fetch origin`. 브랜치의 로컬 커밋과 `origin/<브랜치>`가 같은지 보고, 다르면 어느 쪽이 리뷰 대상인지 오너에게 묻습니다.
2. 병합: `git switch master && git pull --ff-only`, 그 뒤 `git merge --no-ff <브랜치> -m "Merge branch '<브랜치>'"`. 충돌이 나면 `git merge --abort`로 되돌리고 충돌 파일을 보고합니다(임의로 풀지 않음).
3. 검사: 병합 결과로 `pnpm verify`. 실패하면 푸시하지 않고 실패 내용을 보고합니다. 로컬 `master`의 병합 커밋을 되돌릴지는 오너에게 묻습니다.
4. 푸시: `git push origin master`(공유 설정상 매번 확인을 받습니다). 그 브랜치로 예전에 열어 둔 PR이 있으면 GitHub이 병합됨으로 표시합니다.
5. 배포 확인: `deploy.yml` 실행을 기다려 결과와 대상 커밋(병합 커밋)을 확인하고, 배포된 사이트(https://kigpand.github.io/trap-platformer/)에서 이번 변경이 실제로 반영됐는지(예: 번들에 새 코드·문자열, 새 파일 응답 200) 확인합니다.
6. 개발 일지: AGENTS.md "개발 일지" 규칙대로 Notion에서 병합 날짜의 행을 먼저 찾아 갱신하고, 없으면 새로 만듭니다. 커밋과 변경으로 확인되는 사실만 씁니다. 쓰지 못했으면 성공처럼 보고하지 않습니다.
7. 보고: 병합 커밋, 검사 결과, 배포 결과, 확인한 내용, 일지 갱신, 확인하지 못한 것을 짧게 알립니다. 병합한 브랜치는 오너가 원할 때만 지웁니다.
